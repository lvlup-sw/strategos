# Strategos 3.0.0-rc.1 + Contracts 0.12.0 consumer-upgrade notice

**Date:** 2026-09-09
**Status:** Released 2026-09-09. `contracts-v0.12.0` and `v3.0.0-rc.1` both tag
`f7a7264`; Contracts 0.12.0 and the thirteen product packages are listed on nuget.org.
Adoption issues are filed in all four consumers (see *Issues*).

Strategos moves **2.10.0 → 3.0.0-rc.1** as a single major pre-release. It carries
everything merged since 2.10.0 (2026-08-07): the correctness-core program that was
labelled `v2.11.0` (PRs #187, #194, #195, #196, #198), the principal and
action-calculus object program labelled `v2.12.0` (PRs #200, #201), and the typed
action-contract, binding-proof, and derived-compensation program labelled `v2.13.0`
(PRs #203, #205, #206). None of those three milestones shipped under its own tag.
`LevelUp.Strategos.Contracts` moves **0.4.0 → 0.12.0** across the same window.

The consumer-facing procedure is the
[3.0 migration guide](../src/content/docs/guide/ontology/migration-v3.md). This
file records who consumes what, the order the two tags must be cut in, and what
was not verified.

---

## Release order — Contracts first, then the product

1. **Tag `contracts-v0.12.0` first.** `publish-contracts.yml` gates it on:
   - the tag version equalling the pinned `<ContractsVersion>` in
     `src/Strategos.Contracts/Strategos.Contracts.csproj` (currently `0.12.0`);
   - regenerate-and-diff: `scripts/contracts-codegen.sh` must leave `Generated/`,
     `schemas/`, and `docs/diagnostics` clean;
   - the breaking-change diff against the **published** baseline — the workflow
     downloads the newest stable version on nuget.org (0.4.0, per a nuget.org
     index query on 2026-09-09; the current tag is deliberately not a baseline)
     and runs
     `scripts/contracts-schema-diff.mjs` with
     `src/Strategos.Contracts/schemas/breaking-changes.allowlist.json`. Every
     narrowing between 0.4.0 and 0.12.0 must be allowlisted or the job exits 1;
   - the builder-fixture corpus must contain **>= 100** cases before pack.
2. **Then tag `v3.0.0-rc.1`.** `publish.yml` versions with MinVer from the tag.

Why that order and not the reverse: `publish.yml` runs `dotnet pack` over the whole
solution (`src/strategos.slnx`) and then pushes **every** `.nupkg` in `./packages`,
Contracts included. The v2.10.0 run pushed `LevelUp.Strategos.Contracts` 0.4.0 as a
duplicate of the package the `contracts-v0.4.0` run had already published. Cutting
the product tag first would therefore publish Contracts 0.12.0 through the product
workflow — bypassing the four Contracts gates above — and the core package's nuspec
depends on the pinned Contracts version, so the product cannot be pushed against a
Contracts version that does not yet exist on the feed.

## Consumer-first rule for Contracts

The generated `AgwfCode` enum carries `JsonStringEnumConverter<AgwfCode>` with
per-member `JsonStringEnumMemberName`, so it round-trips by name and **throws on a
member it does not know**. A consumer still on 0.4.0 cannot deserialize a payload
carrying any of `AGWF035`–`AGWF045`. Consumers restore 0.12.0 before any producer
on 3.0.0-rc.1 emits diagnostics or workflow definitions to them. The same
narrowing rule applies to `ActionPredicateV1` (0.10.0): unknown discriminators are
rejected rather than read as `custom` or `true`.

The intermediate versions and what each added are tabulated in section 1 of the
migration guide; the one-line summary is 0.5–0.8 add `AGWF035`–`AGWF038`, 0.9 adds
the ontology contract decorators, 0.10 adds typed predicates (narrowing), 0.11 adds
`ActionReferenceV1` and `AGWF039`–`AGWF043`, and 0.12 adds `inverseAction`,
`AGWF044`–`AGWF045`, and the `requiredOnFailure` conditional.

## Housekeeping this release removed

`spikes/typespec-contracts`, which **exarchos#1125** cites as the TypeSpec
substrate reference, was deleted from this repository on 2026-09-09 (commit
`10c9f20`, alongside `evals/captured` and `verification/`). The authoritative
TypeSpec sources are `src/Strategos.Contracts/**/*.tsp`; exarchos#1125 should be
re-pointed there before the link goes stale in someone's checkout.

## Verification the maintainer can run after a consumer lands

- `dotnet restore` in the consumer resolves exactly one `LevelUp.Strategos.Contracts`
  version (0.12.0) across every `project.assets.json`.
- A consumer-side deserialization test round-trips a `WorkflowDefinitionV1`
  carrying `action` and `compensation.inverseAction`, and an `AgwfCode` of
  `AGWF045`, without throwing.
- For a Newtonsoft-serializing Marten store: the `jsonb_typeof(data->'Phase')`
  query on every saga table returns `'string'`, or the ordinal rewrite has been
  applied, before the 3.0 build starts.
- `bash scripts/contracts-codegen.sh` leaves this repository's working tree clean.

## Not swept

Things this notice did **not** verify; treat them as open rather than as absent.

- Whether valkyrie carries any transitive Contracts reference through a package
  this sweep did not open. (Its direct pin is confirmed: 2.8.0, read from
  `src/Valkyrie/Directory.Packages.props` when the adoption issue was filed.)
- Whether dynatoi's custom `IObjectSetProvider` implementations compile against
  the 2.8–3.0 provider surface. Only the package pins were read, not the
  implementations.
- Whether basileus binds `AgwfCode` in code today (the 2026-08-23 notice found it
  only in prose ADRs). If that changed, the deserialization hazard is live rather
  than latent.
- The five `.tsp` files with "Exarchos's TypeScript enum round-trips" claims
  (`GateClass`, `ForkTrigger`, `OntologicalLifecycle`, `Envelope`, `IntentEnvelope`)
  flagged on 2026-08-23 were not re-checked against exarchos.
- Whether any consumer's Marten store uses Newtonsoft. Strategos cannot detect it
  and this sweep did not open consumer `StoreOptions`.
- The `contracts-v0.12.0` gates other than the schema diff were read from the
  workflow file, not executed. The schema diff itself was dry-run on 2026-09-09
  against the 0.4.0 nupkg downloaded from nuget.org (the index listed 0.2.0,
  0.3.0 and 0.4.0): exit 0, twelve breaking changes, every one matched by an
  allowlist entry. A newer Contracts version published between that query and
  the tag would change the baseline the workflow selects.
