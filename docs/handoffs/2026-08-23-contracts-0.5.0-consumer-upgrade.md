# Contracts 0.5.0 consumer-upgrade notice — the `AGWF035` diagnostic code

**Date:** 2026-08-23
**Status:** Consumer set verified 2026-08-23; the one real consumer is notified.

`LevelUp.Strategos.Contracts` moves **0.4.0 → 0.5.0**, adding one AGWF diagnostic
code: `UnreachableTermination` / `AGWF035`.

The addition is schema-additive (a new enum member and a new catalog entry), so it
is a minor bump — but the **upgrade sequences consumer-first**. `AgwfCode` carries
`[JsonConverter(typeof(JsonStringEnumConverter<AgwfCode>))]` with per-member
`[JsonStringEnumMemberName("AGWF0xx")]`, so it round-trips by *name* and the
converter throws on a member it does not know. A consumer still pinned to 0.4.0
cannot deserialize a payload carrying `AGWF035`.

### A stale claim this surfaced — now corrected

`AgwfCode`'s doc asserted that its member names are *"the stable contract
Exarchos's TypeScript enum round-trips against by name (not ordinal — INV-5)"*.
**No such enum exists in exarchos** — searches for `AgwfCode`, `AGWF035` and
`agwf` all return nothing, against a checkout of the repo itself. The seam was
planned (`docs/designs/2026-05-24-slice-b-convergence-close.md:62` records it as
exarchos T6) and never landed.

Corrected in this PR. Two details are worth recording, because the obvious fix
was wrong:

- **There were two independent source carriers, not one.** The JSON schema's
  description comes from `Diagnostics/AgwfCatalog.tsp`, but `AgwfCode.g.cs`'s
  `<summary>` is a **hardcoded string literal** in
  `src/Strategos.Contracts.Codegen/AgwfCatalogEmitter.cs` — the emitter reads no
  `description` field from any schema. Editing only the `.tsp` and regenerating
  would have left the C# XML doc stale.
- **The codegen guard cannot catch that.** It re-runs codegen and diffs the
  output against what is committed, so it proves generated output matches its
  generator — never that the prose is true. A half-fix would have gone green.

The replacement states the property that is actually enforced: `JsonStringEnumConverter`
plus per-member `JsonStringEnumMemberName` make the NAME the wire identity for any
consumer, in any language.

**Not swept:** five other `.tsp` files (`GateClass`, `ForkTrigger`,
`OntologicalLifecycle`, `Envelope`, `IntentEnvelope`) make similar
"Exarchos's TypeScript enum round-trips" claims about *different* enums. Those were
not verified either way here — `main.tsp` says exarchos derives Zod from the
schemas, so some are likely true. They deserve a deliberate sweep, not a
find-and-replace.

The consequence for sequencing is favourable: with exarchos carrying no AGWF
surface, `AGWF035` has exactly one deserializing consumer to get ahead of.

## Issue filed

**lvlup-sw/basileus#489** — *Bump LevelUp.Strategos.Contracts to 0.5.0 alongside the
Strategos 2.11.0 upgrade*.

Note the framing shifted once basileus was actually read. The deserialization hazard
above is **latent, not live**: basileus references AGWF codes only in prose ADRs and
never binds `AgwfCode` in code. Its concrete obligation is *version unification* —
`Directory.Packages.props:20` pins Contracts directly at `0.4.0` because the 2.9.1
Strategos line drags `0.3.0` transitively and transitive pinning is off. Strategos
2.11.0 drags `0.5.0`, so taking that bump without moving the direct pin splits the
graph, and `GateClassSourceTests` (which reads every `project.assets.json` and fails
on a non-singleton union) goes red. The two bumps must move in one commit.
